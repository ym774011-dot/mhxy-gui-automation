## 2. (327,345) 用途推理（静态证据链）

### 2.1 事件序列现场（task_sequence_autosave.json :203-406）

「抓鬼」任务实际有 **6 个事件**（注意：任务书写的「5 个事件」漏了最后一个）：

| # | var_name | 类型 | 内容 | pre/post | on_error |
|---|---|---|---|---|---|
| 1 | 函数调用5 | function | `ZGUI.zhuagui_take_task`（**旧版**，见 §2.4） | 2.0 / 1.5 | skip |
| 2 | **鼠标点击6** | click | **右键 (327,345)**，background=true，press_delay=0.1，verify=false，probe=327/345，verify_retries=3，verify_threshold=30，**jitter_x=6, jitter_y=5** | 1.0 / 1.5 | skip |
| 3 | 图像识别4（名「使用天眼」） | function | `ZGUI.zhuagui_use_tianyan` | 1.5 / 2.0 | skip |
| 4 | 函数调用1 | function | `ZGUI.main`（= zhuagui_enter_battle 一键进战） | 1.5 / 2.0 | skip |
| 5 | 图像识别5（名「战斗中」） | image | `自动战斗.bmp` **wait_disappear**，region [332,261,70,22] | 2.0 / 1.5 | retry |
| 6 | 图像识别5（名「图像识别 5」） | image | `飞行符.bmp` 右键点击，region [27,248,255,103]，**additional_click: 左键 (312,229) = 回长安红点** | 2.0 / 1.5 | skip |

事件 2 的语义只有放在「事件 1 之后、事件 3 之前」这个位置才能解读。

ZGUI.py / core/ 里**没有任何代码引用 (327,345)**（全库 grep 无命中）——它不是代码硬编码，是 GUI 事件编辑器里人工录制的坐标。

### 2.3 正向证据：为什么是「右键关闭对话框」

1. **位置**：(327,345) 落在钟馗对话/任务指引弹窗的区域 x[11,650] y[240,520]（ZGUI.py:663 注释「对话框约 x[11,650] y[240,520]」），且恰好在 `_zhongkui_close_dialog` 的第二候选右键带 `x[120,340] y[300,400]`（ZGUI.py:676）内——与代码中"框内空白处右键"的落点带完全吻合。
2. **交互语义**：右键在框内任意处=关闭（ZGUI.py:658-659：「对话框内任意位置右键即可关闭」）；右键在场景地面=移动指令。
3. **因果需要**：事件 1 用的是**旧版** `zhuagui_take_task`（:339），它接完任务**不关对话框**（只有 v2 `close_dialog=True` 才关，:716-717）。而事件 3 `zhuagui_use_tianyan` 要右键天眼符——天眼符图标 (232,354) **也在弹窗区域内**。若弹窗不先关掉，事件 3 的右键会点到弹窗上而不是物品上。ZGUI.py:695-696 注释原话：「接任务后弹任务指引弹窗，需在对话框内右键关闭……否则弹窗遮挡后续天眼瞬移」。
4. **时序吻合**：pre_delay 1.0s（等事件 1 的弹窗弹出）→ post_delay 1.5s（等弹窗关闭动画）。

**推理**：事件 2 是用户对「旧版 take_task 不关弹窗」这一缺口的手工补丁。

### 2.4 需要用户确认的问题（无法从静态分析确定）

1. 录制「鼠标点击 6」时，点 (327,345) 关掉的是**接任务后弹的任务指引弹窗**，还是钟馗对话本体？（两者都右键关闭，静态不可分）
2. 当时弹窗是否确实遮住了天眼符图标 (232,354)？（若是，则事件 2 是硬依赖，不能删）
3. 是否存在「事件 1 成功但弹窗没弹出」的情形？（若有，事件 2 的右键会落到场景地面触发移动）

### 2.5 顺带发现（一致性检查）

- **事件 1 用旧版接任务**：`zhuagui_take_task`（:339，固定坐标块 116,305-195,319 点一次）而非红字检测的 `zhuagui_take_task_v2`（:690）。工程侧若后续把链路统一到 v2，事件 2 的语义会变（v2 自带关弹窗），需同步评估删除事件 2。
- **JSON 事件顺序与 var_name 有错位**：事件 3 的 var_name 是「图像识别4」但类型是 function；事件 5/6 的 var_name 都是「图像识别5」。不影响执行，但说明该序列是手工拼装+复制的，值得在 GUI 里过一遍。
- 任务书说「5 个事件」，实际 6 个（见 §2.1）。

## 3. jitter ±6/±5 影响评估

### 3.1 机制（core/task_engine.py:1080-1090）

```python
_jx = abs(int(params.get("jitter_x", 0) or 0))   # =6
_jy = abs(int(params.get("jitter_y", 0) or 0))   # =5
if _jx or _jy:
    x = x + random.randint(-_jx, _jx)            # 客户区像素域直接偏移
    y = y + random.randint(-_jy, _jy)
```

- 偏移发生在 `_do_click` 之前、验证逻辑之前；实际落点均匀分布于 **[321,333]×[340,350]**（12×10 px 窗口）。
- 引擎日志 `点击 ({x},{y})` 记录的是**已含 jitter 的落点**（:1119）——这可以直接用来验证 jitter 是否生效（见 §4.4）。

### 3.2 会不会偏出目标

**目标区域尺寸未知**是前提，所以分两种情形：

| 情形 | 目标区尺寸 | 落点窗口 12×10 px 是否安全 |
|---|---|---|
| 弹窗关闭（本文假设） | 框内任意处有效，≈639×280 px | **安全**，余量 >50 px；且远离文字行 y[414,454]（右键文字行可能点中链接不关闭，ZGUI.py:663-664），y 窗口上限 350 << 414 |
| 小按钮/图标（假设不成立时） | 典型 14~20 px 文字块 | ±6/±5 可能偏出——但 §2.2 已排除所有已知小目标 |

**结论**：对已知证据支持的唯一用途（关弹窗），jitter 无害；风险不在 jitter 本身。

### 3.3 真正的风险点（与 jitter 无关，`verify:false` 放大了它）

1. **无到达验证**：`verify:false` 跳过验证分支（task_engine.py:1095），`probe_x/probe_y/verify_retries/verify_threshold` 全部是死配置。若弹窗没弹出或已提前关闭，右键落到场景地面 = **移动指令**，角色走离钟馗/走离天眼可用位，事件 3~5 连锁失败，最终表现正是「超时未完成」。on_error=skip 使该事件永不报错，错误被静默吞掉。
2. **失败传播链**：事件 2 skip → 事件 3 天眼右键点到弹窗 → 瞬移没发生 → 事件 4 `ZGUI.main` 找不到野鬼 → 「超时未完成」。**这与你「可能比调 timeout 更接近根因」的判断一致**：症状相同（inbattle 类），根因在上游。
3. **矛盾点**：`verify_threshold:30 / verify_retries:3` 已配置，说明录制时本想验证；`verify:false` 是后来关掉的（可能因为验证误报）。若要低成本加保险，把 `verify` 改回 `true` 即可启用现成的 `click_verified`（像素色差对比，probe 点在框内，弹窗关闭后颜色必变，天然适配）——**但这是行为变更，须单独立项实测，不要混进本次 A/B**。

### 3.4 与 ADR-0004 的冲突（确认）

- ADR-0004 决策第 2 条：抖动偏移须在**游戏坐标域**计算（pixel_to_game / game_to_pixel），落点转回客户区像素再 PostMessage。
- 事件级 jitter（2026-09-03 新增）在**客户区像素域**直接偏移，两条机制并存且口径不一致。
- ADR-0004 的抖动设计配「到达验证兜底」（R4），事件级 jitter 没有——本事件恰是 `verify:false`，双重失去兜底。
- 缓解因素：对**本事件**（关弹窗）而言，像素域偏移无实际危害（目标区巨大）；冲突是**规范层面**的，影响的是将来把 jitter 推广到小目标点击时。建议留给 engineering-lead 在 Phase 4 集中重构时收敛（ADR-0004 状态本就是「实现待集中」），本次不改代码。

## 4. A/B 执行方案（命令级设计，未启动）

### 4.0 前提与限制（必读）

- **jitter 只存在于事件点击**。`run_unlimited_test.py` 走的是 `zhuagui_do_round` 链路，**不含事件 2**，因此本次 A/B 的载体是 **GUI 任务序列**，不是 T2 启动器。T2 的 jsonl/统计口径在此只能提供参照基线，不能直接做分组统计。
- 测量依据：任务引擎对每个事件都写日志（`logs/automation.log`），其中事件 2 的 `点击 (x,y) button=right` 记录的是**含 jitter 的实际落点**。
- **改 autosave.json 前必须先关 GUI**：`task_sequence_autosave.json` 是 GUI 自动保存文件，GUI 开着时手改会被回写覆盖。

### 4.1 分组开关（最小改动方案：直接改 JSON，不加代码开关）

改两个字段、不动任何代码：

```
组 A（jitter 归零）: "jitter_x": 0, "jitter_y": 0
组 B（现状基线）  : "jitter_x": 6, "jitter_y": 5   （即当前值）
```

操作（GUI 已关闭时）：

```bash
cd /e/DS/mhxy-gui-automation
# 先备份（一次性）
cp data/task_sequence_autosave.json data/task_sequence_autosave.json.bak_jitter_ab

# 切组 A
python - <<'PY'
import json
p = "data/task_sequence_autosave.json"
d = json.load(open(p, encoding="utf-8"))
ev = next(e for t in d["tasks"] if t["name"] == "抓鬼"
          for e in t["events"] if e.get("var_name") == "鼠标点击6")
ev["params"]["jitter_x"] = 0
ev["params"]["jitter_y"] = 0
json.dump(d, open(p, "w", encoding="utf-8"), ensure_ascii=False, indent=2)
print("组A 已生效: jitter=0/0")
PY
# 切回组 B：同上，把 0 改回 6 / 5
```

> 不建议加命令行开关：事件参数归 JSON 所有，加开关意味着改 task_engine 的参数覆盖逻辑，违反「最小改动」，且 GUI 回写会绕过开关造成假对照。

### 4.2 必须两组一致的参数（控制变量）

| 参数 | 值 | 出处 |
|---|---|---|
| 角色/窗口 | 二号美人，同一游戏窗口，**客户区尺寸不得变**（(327,345) 是客户区像素） | group1/settings.json |
| `timeout` | **不设**（走隐式默认 20.0s）——事件 4 `ZGUI.main` 的 kwargs 为空 | ZGUI.py:777 签名默认 |
| `wait_dialog` | **不设**（走隐式默认 1.2s） | 同上 |
| 事件 pre/post delay、loop_delay=2.5 | 不动 JSON 其它字段 | autosave.json |
| 背包 | 保持打开 | 硬约束 |
| 节奏 | 由 loop_delay + 各事件 delay 决定，约 15~30s/轮，两组天然一致 | autosave.json |

> 注意 GUI 事件编辑器里 `ZGUI.main` 的提示文字仍写「默认8」，与代码默认 20.0 不符（T2 已报告）。A/B 期间**不要**在 GUI 里改这两个参数，避免引入第三个变量。

### 4.3 轮数与执行顺序

- 每组 **≥30 轮**（下限），建议 50。
- 顺序建议 **ABBA**（A30 → B30 → B30 → A30）跨两次会话执行，平衡服务器负载/时段漂移；单会话内 A/B 各 30 也可接受但解释力弱一档。
- 样本量警告（S0-observability.md §7 同款纪律）：n=30/组时，Wilson 95% CI 在基线 OK 率 50% 处宽约 ±18pp——**只能检出粗大效应**；若两组差异 <15pp，CI 必然重叠，需加跑到 80~100 轮/组再下结论。**先看 CI 是否分离，再看点估计。**

### 4.4 每组的度量命令

跑完后（假设 A 组跑批时段已知，或用日志时间戳切窗）：

```bash
cd /e/DS/mhxy-gui-automation

# ① 事件 2 实际落点分布（验证 jitter 是否生效；A 组应全部=327,345，B 组应散布在 321~333×340~350）
grep -oE "点击 \((32[0-9]|33[0-9]),3(4[0-9]|5[0-9])\) button=right" logs/automation.log | sort | uniq -c

# ② 事件 2 执行次数 = 开始轮数
grep -cE "点击 \(3[0-9]{2},3[0-9]{2}\) button=right" logs/automation.log

# ③ 事件 5（自动战斗 wait_disappear）与事件 6（飞行符+回长安）完成情况 = 轮次走到哪一步
grep -cE "图像识别.*成功|wait_disappear" logs/automation.log

# ④ 事件 4（ZGUI.main）失败线索：超时未完成 / 无野鬼目标
grep -cE "超时未完成|无野鬼目标" logs/automation.log
```

**判读口径**（每组内）：
- `轮完成率 = 事件 6 完成次数 / 事件 2 执行次数`
- 若 B 组完成率显著低于 A 组 → jitter 对该点有害 → 保持归零；
- 若两组 CI 重叠 → jitter 对该点无害（与 §3.2 的先验一致），jitter 去留交由反外挂策略决定；
- **无论哪组赢，都必须分层看**：用 ①的落点分布 + ③④的分事件失败分布，确认失败究竟发生在事件 2（点偏/没关掉弹窗）还是事件 3/4（天眼/进战）。若失败集中在事件 3 之后的链条，那么 jitter 是无辜的，根因是 §3.3-1 的「弹窗未关时右键落地面」——这是本 A/B 最有价值的可能产出。

### 4.5 jitter 归零的反外挂风险评估与补偿

| 维度 | 评估 |
|---|---|
| 暴露面 | 仅事件 2 一个固定像素，每轮 1 次右键，15~30s 间隔 |
| 历史证据 | `logs/automation.log` 显示 2026-08-16 全天存在大量**完全相同坐标**的模板点击（(327,339) 连续数百次、间隔数十秒），未见掉线记录——固定坐标点击在本服的实害缺乏证据（有混杂，非定论） |
| 其余随机性 | 链路其它点击仍是随机化的：ZGUI post_click 全部带随机偏移+贝塞尔轨迹；事件 6 红点带 ±3；Lua RPC ≥0.15s 抖动；press_delay=0.1 固定 |
| 结论 | 短期 A/B（各 30~50 轮、1~2 小时/组）风险**低**，可接受 |
| 补偿建议（若需长期归零） | ① 把随机化从坐标转移到时序：给事件 pre_delay/post_delay 增加随机抖动（需 task_engine 支持 delay jitter，列为 feature 请求，不在本次改）；② 或把 jitter 缩小到 ±2/±2（在 639×280 目标区下安全且保留随机性）——这是比「全归零」更稳的长期形态 |
